# 文書の設計

文書の設計とは, 読者の課題から結論までを, 節の並びとして組み立てる作業である.
本ページは, 書く前の設計メモ, 設計の6要素, 抽象から具体への順序, 節と段落と見出しの規則を定める.
文書の種別ごとの骨格は `references/genres/` に, 文の書き方は `references/writing_rules.md` にある.

## 設計メモ

文書成果物は, 書く前に設計メモを作業用の一時ファイル(`/tmp` など)に書く.
設計メモは次の4つで構成する. 文書に載せるのは, 一文要約だけである.

```
一文要約: この文書は <読者> に <結論> を伝える.
読者表:   references/reader.md の5行
6要素:    課題, 制約, 方針, 結論, 根拠, 代償 を1行ずつ
役割表:   | 節 | この節の結論(1文) | 見せるもの | 一文要約へのつながり |
```

- 役割表で, 一文要約へのつながりを書けない節は削る.
- 一文要約は, 文書の冒頭の段落に入れる.
  一文要約を書けないなら, 結論が決まるまで調査を続ける.

## 設計の6要素

技術文書は, 対象が何を解決するために, どう作られているかを伝える.
この内容を, 次の6要素に分けて組み立てる.

| 要素 | 答える問い |
|------|------------|
| 課題 | 何に困るか. 仕組みが無いと何が起きるか |
| 制約 | 解き方を縛る条件は何か |
| 方針 | どう解くか. 設計の考え方を1文で書く |
| 結論 | 結果として, 何がどう動くか |
| 根拠 | なぜそう言えるか. コード, 実行結果, 文献で示す |
| 代償 | 何を諦めたか. 限界, 前提, 版差 |

6要素は, 文書の種別ごとに次の内容に対応する.

| 要素 | 概念の解説 | 内部実装の解説 | CTF writeup | 論文の解説 | ブログ | 設計書 |
|------|------------|----------------|-------------|------------|--------|--------|
| 課題 | 仕組みが無いと起きる問題 | 利用者から見た疑問 | フラグの取得 | 研究課題 | 読者が困る状況 | 課題と要件 |
| 制約 | 計算量, メモリ | 性能, 互換性, ロック | 緩和策, 実行環境 | 既存手法の限界 | 環境, 版 | 非機能要件 |
| 方針 | 仕組みの考え方 | 設計の考え方 | プリミティブの連鎖 | 提案の核心 | 解決の考え方 | 設計方針 |
| 結論 | 構造と操作 | 到達経路と状態変化 | 最終の攻撃コード | 主な結果 | 手順と結果 | 設計結論 |
| 根拠 | 手で追う例 | 抜粋, 観測点 | 実行結果 | 評価の表と図 | 実行例 | 案の比較 |
| 代償 | 苦手な入力 | 版差, 前提 | 成功率, 前提 | 限界 | 制限 | 残るリスク |

## 結局なにかの検査

書き終えた文書に, 次の2つを問う.

1. 冒頭の段落だけを読んで, 課題と結論を言えるか.
2. `check_doc.py` が表示する骨格(見出しと各節の冒頭文)だけで, 6要素を拾えるか.

どちらかに答えられない文書は, 読者に, 結局なにを言いたいのかという疑問を残す.
拾えない要素があれば, 節を足すか, 節の冒頭文を書き直す.

## 冒頭に置くもの

文書の冒頭には, H1 の直後に次の5点を置く.

1. 主題の定義を1から2文で書く.
   スケジューラなら, CPU 数より実行可能なタスクが多いときに, どのタスクをどの CPU で動かすかを決める処理, と書く.
2. 一文要約を書く. 読者が文書から持ち帰る結論を1文にする.
3. 対象読者と前提知識を2行で書く. 前提の外の語は, 初出で定義する.
4. 本ページで扱う範囲と, 扱わない範囲を書く. 範囲外の話題は, 末尾か別ページに置く.
5. 4節以上の文書では, 節の一覧を書く.

実装を読む技術資料では, 定義の前に対象の版の1行(`対象: Linux 7.2.8, x86-64`)を置く.

## 抽象から具体への順序

文書と節は, 抽象度の高い文から低い文へ向かって書く.
抽象度は, 次の3段で数える.

| 段 | 内容 | 例 |
|----|------|----|
| L1 主張 | 結論を1文で書く | パイプは, 書き込みを末尾のページに追記する |
| L2 仕組み | L1 が成り立つ理由と, 構成要素の関係 | `pipe_buffer` が, ページとページ内の有効範囲を持つ |
| L3 具体 | 値, コード, 出力, 図 | 100 バイトを2回書くと, 同じページの有効範囲が 200 バイトになる |

1. 節は L1 の文で始め, L2, L3 の順に進む.
2. L3 の後に, 例から読み取れることを1文で書き, L1 へ戻る. 書き方は `references/examples.md` に従う.
3. 4節以上の文書は, 冒頭の近くに全体像(図か表)を1つ置く. 各節は, 全体像の1要素を拡大する.
   全体像の要素名を, 節の見出しに使う.
4. コードや出力を並べただけの節と, 例のない主張だけの節は, どちらも L1 から L3 のどれかが欠けている.
   欠けた段を足す.

## 節の規則

1. 節の冒頭文に, その節の結論を書く. 冒頭文だけを読んだ読者が, 節の結論を持ち帰れるようにする.
2. 節の冒頭文は, 前の節の結論が生んだ問いに答える形で始める.
   前の節が `平坦な配列は 512 GiB を要する` で終わったら, 次の節は `4段のテーブルは, 使う範囲の表だけを確保する` で始める.
3. 節の移り変わりは, 次の節の冒頭文が担う. 節の末尾にある次の節の予告(`次に〜を見る`)は削る.
4. `本節では〜を説明する` のような予告で節を始めない. `outline_ja.py` は, この形を FAIL にする.
5. 1節は2段落以上を目安にする. 1文だけの節は, 前後の節に統合する.

## 段落の構成

段落は, 結論, 理由, 例, 補足 の順に書く.
長い文書に限り, 末尾に結論を再掲する.

| 段 | 内容 | 注意 |
|----|------|------|
| 結論 | 主張を1から2文で書く | 理由が必要な語は, ここで使わず理由で説明する |
| 理由 | 結論が成り立つ根拠 | 結論で生じた疑問に, この段で答える |
| 例 | 具体的な値, コード, 手順 | コードの前に目的を書く |
| 補足 | 例外, 制限, 対比 | 理由より後ろに置く. 注意書きは `>` を使う |
| 再掲 | 判断基準や次の行動 | 条件を満たすときだけ書く |

## 談話の規則

1. 文が疑問を生んだら, 次の文でその疑問に答える.
   `変換情報が大量に必要になる` と書いたら, 直後で変換情報とは何か,
   なぜページ数に比例するかを書く.
2. 対比と補足は, 理由を述べ終えた後に置く.
3. `両者は異なる` のように, 中身のない予告文で終えない.
   違いを同じ段で書く.
4. 隣接する二文の関係(理由, 具体化, 対比, 補足)を説明できなければ,
   接続詞を足すか, 文を並べ替える.
5. 箇条書きに項目間の因果や対比があるなら, 文で書く.

## 見出し

1. 見出しは内容を予告する名詞句にする.
   結論の一部を命題にしない.
   `中核`, `その他`, `まとめ` などの空語や, `A / B と C` 型の複合見出しは使わない.
2. H1 の主題語を, 冒頭の定義文と節の見出しに引き継ぐ.
   主題と無関係な節は, 冒頭で主題との関係を書く.

## 概念の解説の節順

データ構造やアルゴリズムなど, 1つの概念を説明する資料は, 次の順に節を置く.

| 順 | 節 | 内容 |
|----|----|------|
| 1 | 解く問題 | この仕組みが無いと何に困るかを, 具体的な状況で書く |
| 2 | 最小の具体例 | 値を1つずつ手で追える大きさの例を, 図か表で示す |
| 3 | 仕組みと理由 | 例で起きたことが, なぜ成り立つかを書く |
| 4 | Linux での実装 | 実在の構造体, 関数, ファイルと, 上の仕組みの対応を書く |
| 5 | コード | 目的, 抜粋の範囲, 省略した内容を書いてから示す |
| 6 | 注意点 | 版差, 前提条件, 誤解しやすい点. 1節にまとめる |

- 注意点, 版差, ビルド設定の分量は, 本文の20%以下にする.
- 注意点が本論の理解に必要なら, 3 の節で理由とともに書く.
- 定義より先に, 解く問題の節を置く.

## 根拠の書き方

1. 性能や性質を主張したら, その根拠を同じ節で3文以内に書く.
   悪い例と良い例を, 赤黒木の高さの説明で示す.

   ```
   悪い例: 色の制約で高さが O(log n) に収まる.
   良い例: 各ノードから葉までの黒ノード数が等しく, 赤が連続しないので,
           最長の経路は最短の経路の2倍以下になる.
           そのため高さは O(log n) に収まる.
   ```
2. 用語を `畳み込まれる` のような比喩で終えない. 何がどう変わるかを書く.
3. 根拠をコードに求めるなら, `file:line` を示す. 書式は `references/citations.md` に従う.

## 注意書きと補足の置き場所

1. 版差, ビルド設定, 範囲外の話題, 誤解しやすい点は, 本論の後ろの1節にまとめる.
2. 補足の分量は, 本文の20%以下にする.
3. 本論の理解に必要な条件は, 補足にせず, 理由の段で書く.
4. 注意書きは, 読者がその誤りを犯す場面があるときだけ書く.
5. 書く前に, その文を消して読者が困るかを考える. 困らなければ削る.
6. 否定文は全文の10%以下にする. 肯定の説明を先に書く.
7. 保証する範囲と保証しない範囲を比べるときは, 表の列にせず,
   保証する範囲を文で書き, 例外は `>` の注意書きにする.

## 作業の記録と本文を分ける

- 本文は, 調査の経緯, 指示の内容, 実施した作業から切り離す.
  該当する語は `指定された`, `今回`, `ユーザー指定`, `作業範囲`, `確認した`, `未実施` である.
- 実施した検証と実施していない検証は, 検証記録のページにまとめる.
- 版の情報は, 冒頭の1行 (`対象: Linux 7.2.8, x86-64`) に限る.

## 結論の再掲

次の全てを満たすときだけ書く.

- 3節以上の文書, または結論から末尾まで長い回答である.
- 判断基準や次の行動など, 新しい情報を1文以上含められる.

短い会話の回答には付けない. 言い換えだけの総括は書かない.

## 削除テスト

書き終えたら, 次の2つを試す.

1. 根拠(例, 出力, 図)の節を消したと想定する. 残った節だけで一文要約を言えることを確かめる. 言えなければ, 主張を足す.
2. 主張(各節の冒頭文)を消したと想定する. それでも文書が成り立って見えるなら, 根拠を並べているだけである.

## 種別ごとの構成

| 種別 | 構成 | 詳細 |
|------|------|------|
| 回答 | 結論, 根拠, 必要な但し書き | 本ページ |
| 調査報告 | 結論, 観測した事実, 推論, 未確認事項 | 本ページ |
| レビュー | 重大度順の指摘, 各指摘に場所と再現条件 | 本ページ |
| 設計書 | 課題と要件, 制約, 設計方針, 設計結論, 検討した案と判断理由, 残るリスク | 本ページ |
| 概念の解説 | 解く問題, 最小の具体例, 仕組みと理由, 実装, コード, 注意点 | 本ページ |
| テクニカルブログ | リード, 問題, 解決の全体像, 手順, 検証, 制限 | `references/genres/tech-blog.md` |
| CTF writeup | 概要, 解析, 攻撃の方針, 実装, フラグ, 知見 | `references/genres/ctf-writeup.md` |
| 内部実装の解説, コード読解 | 公開 API, 到達経路, 管理構造, 状態変化, 設計の理由, 観測点 | `references/genres/internals.md` |
| 論文の解説 | 書誌, 一文要約, 課題, 提案の核心, 手法, 評価, 限界と考察 | `references/genres/paper.md` |
