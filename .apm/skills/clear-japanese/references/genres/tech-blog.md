# テクニカルブログ

テクニカルブログとは, 検索などで訪れた読者が, 自分の問題を解くために読む Web 上の技術記事である.
本ページは, ブログ記事の骨格と, ブログに固有の規則を定める.
共通の規則は `references/document-design.md` にある.

## 6要素との対応

設計の6要素は, ブログでは次の内容に対応する.

| 要素 | ブログでの内容 |
|------|----------------|
| 課題 | 読者が困っている状況. エラーメッセージ, 遅さ, 分からない挙動 |
| 制約 | 環境, 版, 前提とする構成 |
| 方針 | 解決の考え方を1文で書く |
| 結論 | 手順と, その結果 |
| 根拠 | 実行例, 計測値 |
| 代償 | 制限, 試していない環境 |

## 骨格

ブログ記事は, 次の順に節を置く.

| 順 | 節 | 内容 |
|----|----|------|
| 0 | リード | 結論, 対象読者, 環境と版. 読者が10秒で自分向けかを判定できる量にする |
| 1 | 問題 | 読者が遭遇する状況を, 再現できる形で書く |
| 2 | 解決の全体像 | 方針を1文で書き, 手順の全体を図か表で示す |
| 3 | 手順, 仕組み | 1節に1手順. コマンド, 出力, 読み取り文の順に書く |
| 4 | 検証 | 解決したことを示す実行例か計測値 |
| 5 | 制限 | 試していない環境, 既知の問題 |
| 6 | 参考 | 一次資料 |

タイトルは, 問題か結論を含む名詞句にする(`pipe への書き込みが遅い原因と対処`).

## 固有の規則

1. リードの1文目から, 課題か結論を書く. 空疎な前置き(`近年, 〜が注目されている`)は読者の判定を遅らせる.
2. 予告だけの導入(`本記事では〜を紹介します`, `それでは見ていきましょう`)は書かない.
3. 太字は1節に1つまでにし, その節の結論に使う.
4. コマンドと出力は, 実行したものだけを書く. 出力は貼り付ける.
5. まとめの節は, 新しい情報(判断基準, 次の行動)があるときだけ置く. 本文の言い換えだけなら削る.
6. 環境と版は, リードに1行で書く. 版によって挙動が変わる記事では, 確かめた版の範囲も書く.
7. 文体は, である調にする. 利用者が, です, ます調を指定したら従う.

## 修正例

悪い出力:

```
# Rust の非同期処理について

近年, Rust の非同期処理が注目を集めています.
本記事では, tokio を使った非同期処理について紹介します.
それでは見ていきましょう.
```

修正後:

```
# tokio の spawn がタスクを並行に実行する仕組み

`tokio::spawn` は, 渡した処理をタスクとしてランタイムに登録し, 呼び出し元を待たせずに戻る.
本記事は, 2つの HTTP 要求を並行に送る例で, 登録から実行までの流れを説明する.
対象読者は, Rust の `async fn` を書いたことがあるプログラマである.
環境: Rust 1.85, tokio 1.43, Linux x86-64.
```

直した点:

- タイトルを, 記事の結論を予告する名詞句にした.
- 前置きと予告を削り, 1文目に結論を置いた.
- 対象読者と環境をリードに入れ, 読者が自分向けかを判定できるようにした.

## 検査

次のコマンドで, 表記, 骨格, 図, 抜粋を検査する.

```
python3 <skill>/scripts/check_doc.py <file> --genre blog
```

`outline_ja.py` は, リードに環境か版の記述が無いときに INFO を出す.

## チェックリスト

- [ ] リードだけで, 課題, 結論, 対象読者, 環境が分かる.
- [ ] 前置きと, 予告だけの導入が無い.
- [ ] 各手順に, コマンド, 出力, 読み取り文がある.
- [ ] 検証の節に, 実行例か計測値がある.
- [ ] まとめの節は新しい情報を含む. 含まなければ削った.
