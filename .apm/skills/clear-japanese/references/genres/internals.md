# 内部実装の解説とコード読解

内部実装の解説とは, 設計文書に書かれていない内部の挙動を, ソースコードを根拠に説明する文書である.
コード読解の資料とは, Linux カーネル, コンパイラ, ブラウザエンジンのような大規模なプロジェクトで, どこに何があり, どの順に読むかを示す文書である.
本ページは, 2つの骨格と, 到達経路, 設計の理由, 観測点の書き方を定める.
会話や一般文書には適用しない. 検査は `check_doc.py --genre internals` で行う.

## 6要素との対応

設計の6要素(`references/document-design.md`)は, 2つの資料で次の内容に対応する.

| 要素 | 内部実装の解説 | コード読解 |
|------|----------------|------------|
| 課題 | 利用者から見た疑問 | 読者が理解したい機能 |
| 制約 | 性能, 互換性, ロック, 版 | プロジェクトの規模, 版 |
| 方針 | 実装の設計の考え方 | 読む範囲と読む順序 |
| 結論 | 到達経路と状態変化 | ディレクトリと構造の地図 |
| 根拠 | コードの抜粋, 観測点 | 通し例の経路 |
| 代償 | 版差, 前提条件 | 地図に含めない範囲 |

## 挙動を追う資料の骨格

API からカーネルなどの内部実装を追う資料は, 次の順に節を置く.

| 順 | 節 | 内容 |
|----|----|------|
| 1 | 公開 API | 利用者が呼ぶ関数と, 引数, 戻り値 |
| 2 | 到達経路 | API から内部の関数まで. 各段階の役割と操作対象 |
| 3 | 管理構造 | 経路で使った構造体の定義と, 全体の参照関係 |
| 4 | 状態変化 | 操作の前後の図と, 値の推移 |
| 5 | 設計の理由 | なぜこの構造と経路をとるか |
| 6 | 観測点 | 停止点と, 状態を読む式 |

- 経路の節で使う構造体は, 初出の文で1文の定義を添える. 詳細は管理構造の節に置く.
- 通し例を1つ決め, 経路, 管理構造, 状態変化の各節で同じ値を追う. 通し例は `references/examples.md` に従う.

## API から実装への導線

1. 内部処理は, 利用者が呼ぶ API からの到達経路で説明する.
2. 経路は, 公開 API, 各段階, 操作対象の構造体の順に示す.
3. 各段階の役割と, 操作する対象を文で書く. 関数名の列挙だけでは説明にならない.
4. 必要に応じて, 停止点と内部状態を読む式を添える. 書き方は観測点の節に従う.
5. 複数のトピックに共通する入口(システムコールの受付など)は, 専用ページにまとめる.
   各ページは, 共通入口へのリンクと, そのトピック固有の処理だけを持つ.

## 設計の理由

1. 実装がその形をとる理由を, 制約(性能, 互換性, 並行性)と結びつけて書く.
2. 根拠は, commit message, メーリングリストの議論, `Documentation/` などの一次文書に求める. 出典の書式は `references/citations.md` に従う.
3. 一次文書に書かれた理由と, コードから推論した理由を書き分ける. 推論は `〜と考えられる` で終える.
4. 採らなかった設計(古い版の方式, 他の OS の方式)と比べると, 理由が伝わりやすい. 比べるときは, 違いを同じ段落で書く.

## 大規模コードの地図の骨格

大規模なプロジェクトのコード読解の資料は, 次の順に節を置く.

| 順 | 節 | 内容 |
|----|----|------|
| 1 | 目的 | この地図で理解したい機能を1文で書く |
| 2 | 責務の表 | 関係するディレクトリとファイルを, 責務とともに並べる |
| 3 | 主要な構造 | 中心になる構造体と, 参照関係の図 |
| 4 | 通し例の経路 | 1つの操作が, 責務の表のどこを通るか |
| 5 | 読む順序 | 最初に読むファイルと関数, 次に読むもの |
| 6 | 一次文書との対応 | 設計文書, コメント, テストのどこに説明があるか |

- 責務の表には, 目的に関係するディレクトリだけを載せる. ツリー全体の転載は, 読者に読む範囲を示さない.
- 読む順序は, 通し例の経路に沿わせる.
- 一次文書が実装と食い違うときは, 版と, どちらが正しいかの根拠を書く.

## 観測点

停止点と式を示すときは, 次の列を持つ表にする.

| 列 | 内容 |
|----|------|
| 停止点 | 関数名, または関数からの復帰直後 |
| ソース位置 | `パス:行番号` |
| 調べる対象 | 引数, フィールドなど |
| 分かること | 見えた値から言えること |

式を並べるコードブロックの前に, 停止する場所と目的を書く.
最適化で値が見えない場合の代替手段は, `>` の注意書きにする.

## 前方参照

1. `後述` は, 1つの節で1回までである.
2. 経路の節が使う構造体は, 初出の文で1文の定義を添える. 詳細の節は, リンクで示す.
3. 定義を先に書けないときは, 参照先の節の見出しを書く. 見出しを書けば `後述` は省ける.

## 他のファイルに従う規則

| 内容 | 従うファイル |
|------|--------------|
| 版と取得元, 出典, ソースコードの抜粋 | `references/citations.md` |
| 経路図 | `references/figures.md` |
| メモリ配置図, 状態変化の図 | `references/memory-layout.md` |
| ハンズオン | `references/examples.md` の解答付きの教材 |

本文には対象の版と取得元(`linux-7.2.8` など)だけを書き, ローカルの絶対パスは frontmatter の `source_tree:` に置く.

## 検査

次のコマンドで, 表記, 骨格, 図, 抜粋を検査する.

```
python3 <skill>/scripts/check_doc.py <file> --genre internals --tree <dir>
```

frontmatter に `source_tree:` があり, そのディレクトリが存在すれば, `--tree` は省略できる.
`outline_ja.py` は, 冒頭に `対象:` の行が無いときに INFO を出す.

## チェックリスト

- [ ] 冒頭の1行に版と取得元がある. 本文にローカルの絶対パスが無い.
- [ ] 公開 API からの到達経路を示し, 各段階の役割と操作対象を文で書いた.
- [ ] 経路図の出典に `def`, `call`, `gen` のマーカーがある. 同じ行番号を別の箇所で繰り返していない.
- [ ] 行番号に検索語を併記した.
- [ ] 構造体は, 実際の定義を抜粋した. 省略した範囲の内容を書いた.
- [ ] 状態変化の図は, 操作前と操作後が対で, 同じ識別子と値で追える.
- [ ] 設計の理由の節で, 一次文書の理由と推論を書き分けた.
- [ ] コード読解の資料では, 責務の表を目的に関係する範囲に絞った.
- [ ] `後述` が, 1つの節で2回以上出ていない.
- [ ] ハンズオンに, 期待出力と結果の読み方がある.
