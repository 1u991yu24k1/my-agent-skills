# アンチパターン集

文書を書き終えたら, 似た言い回しが残っていないか照合する.

## T1 出所の分からない語

悪い例 (kernel のドライバ開発で Codex が書いた文):

```
module exit は online flag を落とし, 全 probe を unregister して
grace period を待つ.
```

`module exit`, `online flag`, `probe`, `unregister`, `grace period` の
出所が不明で, 読者の認知負荷が増える.
語数を削った結果, 日本語として成立していない.

修正案:

```
`rmmod` などのドライバアンロード時に, `module_exit` 内で
`unregister_probes()` を呼び出す. この関数は以下を行う.
1. グローバル配列 `probes[]` の `registered` な要素ごとに,
   - `tracepoint_probe_unregister()` を呼び出し,
   - `probes[i].registered` をクリアする.
2. `tracepoint_synchronize_unregister()` を呼び出し,
   非同期処理の完了を待つ.
```

由来不明の英単語が無く, コードと突き合わせられる.
処理を分けて箇条書きにしているので, 長くなっても読みやすい.

## T2 一般語を特殊な意味で使う

`transaction`, `registry`, `generation`, `shape` は,
OS やソフトウェア開発以外の文脈でも使う語で, 意味が文脈で変わる.
文書内で定義せずに使うと, 読者は別の意味に取る.

悪い例:

```
`SUBMIT_VERDICT` は ABI shape と reserved field を検証した後,
`event_id` と `generation` で scan registry を検索する.
存在しない transaction は `-ENOENT`, generation 不一致は `-ESTALE`
を返す.
```

`ABI shape` と `reserved field` は文中で説明されていない.
`ABI` は医学の足関節上腕血圧比検査の略とも読める.

修正方針: 文書内で各語の意味を一度定義し, 実在の構造体名,
関数名, フィールド名で置き換える.

## T3 英単語のサ変動詞化と名詞連鎖

悪い例:

```
seq は drop を含む emit 試行ごとに進む.
```

修正案:

```
`seq` は, イベントの書き込みを試みるたびに 1 増える.
書き込みに失敗した場合も増える.
```

`drop する`, `emit される`, `fold する` のように英単語に `する` を付けない.
名詞を3語以上連ねず, 述語を書く.

## C1 唐突なコードブロック

悪い例: 別の話題の文章の直後に, 説明なしでコードブロックを置く.

```
(別の話題の文章)

(コードブロック)

syscall の lookup は値を userland の buffer にコピーする.
```

読者はコードの目的を知らずに読み始め, 認知を0から組み立てる.
後続の文にも `map value pointer` のような由来不明の語がある.

修正案:

```
map から値を取得する例を示す.
以下のコードは, `bpf` システムコールで bpf map から値を検索する.

(コードブロック)

`lookup.value` には, 検索結果を書き込む先のポインタを指定する.
kernel が検索結果を `value` に書き込む.
```

## N1 否定文の列挙

悪い例:

```
`seq` は drop を含む emit 試行ごとに進み, `generation` は変更しない.
`event_id` は因果関係用で, ring 自身は採番しない.
device 情報は telemetry であり, authoritative な identity ではない.
UAPI に raw kernel pointer は含めない.
```

否定で終わる文が続くと, 結論が何かが分からなくなる.
次の問いで必要性を確認する.

- その否定文は主題を裏付けるか, 直前の文への補足か.
- 否定文を足すと読者は何を得るか. 読むのに必須の情報か.
- 読者の拡大解釈を牽制するだけなら, 直前文と同じ強度で書かない.

補足は `>` の引用で直前の文の直下に添える.
GitHub や Obsidian では危険度に応じて `> [!TIP]`, `> [!WARNING]`,
`> [!CAUTION]` を使い分ける.

```
これは入力値の存在を確認するための user-space 計算を示す.
> XFRM 経路を kernel で動的に実行した証拠ではないことに注意.
```

## M1 分岐のない mermaid

分岐のない呼び出し経路は mermaid にしない. 縦に長くなり, 場所を取る.

悪い例:

```mermaid
flowchart TD
    A[php_execute_script_ex] --> B[zend_execute_script]
    B --> C[zend_compile_file]
    C --> D[zend_execute]
```

修正案: 1段ごとに 2 文字のインデントで表す.

```
php_execute_script_ex()
  → zend_execute_script()
    → zend_compile_file()
      → zend_execute()
```

## D1 疑問に答えずに話題を進める

悪い例:

```
通常の x86-64 ページは 4 KiB だが, 多数のページを扱うと
変換情報も大量に必要になる.
より大きな単位で対応付ければ, ページテーブルや TLB の負担を減らせる.
```

`変換情報` が何かも, なぜ大量に必要かも書かれず, 解決策に進んでいる.
小さいページの欠点が, 結論と理由の間に挟まっている.

修正案: 結論, 理由, 例, 補足の順に並べ, 疑問への答えを次の文に置く.
`references/good_examples.md` の例1に修正例がある.

## D2 中身のない予告文

悪い例:

```
両者は確保方法と失敗時の挙動が異なる.
```

違いを書かずに終わる. 予告した内容は同じ段で書く.

修正案:

```
HugeTLB は, 事前に予約したプールから確保する. プールが足りないと
確保に失敗する. THP は, 条件が合うときにカーネルが自動で割り当て,
合わなければ通常のページに戻る.
```

## D3 見出しと主題の不整合

悪い例:

```
# スケジューラアルゴリズム

## 待機解除と CPU の割り当ては別の処理
```

H1 の語が H2 以降に現れず, H2 は何の節か分からない命題になっている.
ページの冒頭に, 主題の定義, 扱う範囲, 節の構成がない.

修正案: 冒頭にスケジューラの定義と範囲を置き, 見出しは名詞句にする.
`references/good_examples.md` の例2に修正例がある.

## R1 参照先の不明な指示語, 擬人化

悪い例:

```
次に誰をどの CPU で動かすかを選ぶ必要がある.
```

`誰` が指す対象が不明で, 動作主が曖昧になっている.

修正案:

```
スケジューラは, 実行可能なタスクのうちどれを, どの CPU で
実行するか決める.
```

`この`, `上記`, `該当` は, 指す対象が一つに決まるときだけ使う.

## S1 接続詞が消えた箇条書き

箇条書きにすると, 項目間の因果や対比が消える.
項目が並列でなければ, 文で書く.

悪い例:

```
- TLB のエントリ数は有限
- ページが小さいとミスが増える
- Huge Page を使う
```

修正案:

```
TLB のエントリ数は有限である. ページが小さいと, 1 エントリが
カバーする範囲が狭く, ミスが増える. そのため Huge Page を使い,
1 エントリの範囲を広げる.
```

## K1 句点を付けただけの体言止め

述語を省き, 名詞や形容動詞の語幹に `.` だけを付けても, 体言止めは直らない.
`lint_ja.py` は文末が名詞, 記号, 英数字の文を FAIL にする.

悪い例:

```
赤ノードの子は黒.
ハッシュは完全一致を平均的に少ない参照で得るための索引.
検索, 挿入, 削除は O(log n).
```

修正案:

```
赤ノードの子は, 必ず黒である.
ハッシュテーブルは, 完全一致の検索を平均的に少ない参照で行うための索引である.
検索, 挿入, 削除の計算量は, いずれも O(log n) である.
```

## T4 英単語と日本語の無空白接着

地の文の英単語は, 日本語と空白なしで接すると読めない.
`cacheし`, `uncleが` は, 英単語に助詞や活用語尾が付いた形である.
地の文は日本語に直す. 英語のまま残すなら識別子として `` ` `` で囲む.

悪い例:

```
bucket番号に写像し, 同じbucketへ入った要素をcacheしておく.
uncleが赤の場合は, loopを続ける.
```

修正案:

```
キーをバケット番号に変換し, 同じバケットに入った要素を比較する.
叔父ノード(親の兄弟)が赤の場合は, 祖父ノードを対象に処理を繰り返す.
```

## T5 未定義語の並び

`intrusive`, `augmentation`, `uncle`, `pivot`, `wrapper`, `slot` は,
定義なしで使われると, 読者はコードを開くまで意味が分からない.
初出で定義し, 以降は同じ日本語で通す. 対応表は `terminology.md` にある.

悪い例:

```
rb_node を利用者オブジェクトへ埋め込む intrusive な設計.
```

修正案:

```
`rb_node` は, 利用者の構造体の中にメンバとして置く.
このように, 要素自身がノードを持つ方式を, 埋め込み型と呼ぶ.
ノードを別に確保しないので, 挿入時のメモリ確保が要らない.
```

## N2 否定の密度と `保証しないこと` 表

否定で終わる文が全体の1割を超えると, 読者は何が成り立つのかを読み取れない.
N1 は連続した場合の規則で, N2 は文書全体の密度の規則である.
表に `保証しないこと` の列を設けると, 否定文を表に隠すだけで減らない.

悪い例:

```
| 設定 | 目的 | 保証しないこと |
| `KASAN` | 境界外アクセスの検出 | 全バグの検出 |

`RB_EMPTY_NODE` は所属証明ではない.
通常 API は排他もオブジェクト寿命も保証しない.
```

修正案:

```
`KASAN` は, 実行時に境界外アクセスと解放済みメモリの参照を検出する.
検出できるのは, コンパイラが検査コードを挿入した範囲に限られる.

`RB_EMPTY_NODE` は, ノードが木から外れているかを示す印である.
木の所属を調べる必要があるときは, 呼び出し側が自分の規約で管理する.
```

肯定の説明を先に書き, 例外は `>` の注意書きに1つだけ置く.

## L1 作業ログの混入

読者は, 誰が何を指示し, 何を実施したかを知らない.
本文に作業の経緯があると, 読者は参照先を追えない.
該当する語は `指定された`, `今回`, `ユーザー指定`, `作業範囲`, `確認した`, `未実施` である.

悪い例:

```
指定されたローカルソースの Linux 7.2.8 を基準にする.
ユーザー指定のビルド時4段固定は満たしていない.
既存ページはリンク先の存在を確認した. 内容は今回の作業範囲外.
```

修正案:

```
対象: Linux 7.2.8, x86-64.
このカーネルは, 起動時に CPU の対応状況を見て, 4段か5段かを選ぶ.
```

実施した検証と実施していない検証は, 検証記録のページに書く.

## X1 根拠のない性質の主張

性質を主張する文には, 同じ節に根拠を書く.
根拠がないと, 読者は納得できず, 他の箇所にも応用できない.

悪い例:

```
赤黒木は, 二分探索木の高さを色の制約で O(log n) に抑える.
```

修正案:

```
各ノードから葉までの経路は, 同じ数の黒ノードを通る.
赤ノードの子は黒なので, 赤は連続しない. そのため最長の経路は,
最短の経路の2倍以下になる. 高さが要素数の対数に収まるのは, この性質による.
```

## H1 免責が本論より先にある

版差, ビルド設定, 範囲外の話題を主題の定義の直後に置くと,
読者は主題を理解する前に例外を読まされる.
本論の理解に必要でない注意は, 末尾の節に置く.

悪い例: `多段テーブル` の定義の直後に, 4段と5段の選択, `no5lvl`,
ビルド時固定の可否を15行書く.

修正案: 定義, 具体例, 仕組みの後に, 注意点の節を1つ設ける.
`references/good_examples.md` の例4に修正例がある.

## E1 具体例のない API 表

関数名の表を先に見せても, 読者はどの順で呼ぶのか分からない.
3要素の挿入など, 小さい例を手で追った後に, 例で使った関数を表にする.

悪い例: 図を1枚置いた直後に, `rb_link_node`, `rb_insert_color`,
`rb_erase` の役割を名詞止めで並べた表を置く.

修正案: 1, 2, 3 を順に挿入する例を示し, 各挿入で呼ぶ関数を文で説明する.
表は, その後に一覧として添える.

## A1 表と `/` による名詞連鎖

`添字 / entry状態 / rollback` のような並びは, 語の関係を示さない.
名詞を3語以上連ねた表のセルも同じである.

悪い例:

```
| 多段テーブル | 添字 / entry状態 / rollback | 全段の範囲, 公開前初期化, 回収 |
```

修正案:

```
多段テーブルでは, 次の3点が壊れやすい.
- 添字が配列の範囲を超える.
- エントリの状態を取り違える.
- 確保に失敗したとき, 作りかけの枝が残る.
```
