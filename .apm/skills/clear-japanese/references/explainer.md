# 解説資料の組み立て

解説資料は, 読者が仕組みを理解して自分で説明できる状態にすることが目的である.
注意書きの量で正確さを示すことは, 目的に含まれない.
規則を満たしても, 理由と具体例が欠けていれば, 読者は理解に至れない.

## 冒頭に書く3点

1. 主題の定義を1から2文で書く.
2. 対象読者と前提知識を2行で書く. 前提の外の語は, 初出で定義する.
3. 本ページで扱う範囲を書く. 範囲外の話題は, 末尾か別ページに置く.

## 節の順序

| 順 | 節 | 内容 |
|----|----|------|
| 1 | 解く問題 | この仕組みが無いと何に困るかを, 具体的な状況で書く |
| 2 | 最小の具体例 | 値を1つずつ手で追える大きさの例を, 図か表で示す |
| 3 | 仕組みと理由 | 例で起きたことが, なぜ成り立つかを書く |
| 4 | Linux での実装 | 実在の構造体, 関数, ファイルと, 上の仕組みの対応を書く |
| 5 | コード | 目的, 抜粋の範囲, 省略した内容を書いてから示す |
| 6 | 注意点 | 版差, 前提条件, 誤解しやすい点. 1節にまとめる |

- 注意点, 版差, ビルド設定の分量は, 本文の20%以下にする.
- 注意点が本論の理解に必要なら, 3 の節で理由とともに書く.
- 定義より先に, 解く問題の節を置く.

## 具体例の規則

1. 定義した語は, 次の段落か次の節で, 具体例の中で使う.
2. 例の値は, 読者が手で追える個数にする.
   赤黒木なら, 3要素を挿入して再着色が起きる様子を示す.
3. 例を示した後に, 一般化した規則を書く. 規則が先なら, 規則の直後に例を置く.
4. API の表は, 具体例で使った操作を並べる. 例の後に置く.

## 理由の書き方

1. 性能や性質を主張したら, その根拠を同じ節で3文以内に書く.
   悪い例と良い例を, 赤黒木の高さの説明で示す.

   ```
   悪い例: 色の制約で高さが O(log n) に収まる.
   良い例: 各ノードから葉までの黒ノード数が等しく, 赤が連続しないので,
           最長の経路は最短の経路の2倍以下になる.
           そのため高さは O(log n) に収まる.
   ```
2. 用語を `畳み込まれる` のような比喩で終えない. 何がどう変わるかを書く.
3. 根拠をコードに求めるなら, `file:line` を示す.

## 注意書きの規則

- 注意書きは, 読者がその誤りを犯す場面があるときだけ書く.
- 書く前に, その文を消して読者が困るかを考える. 困らなければ削る.
- 否定文は全文の10%以下にする. 肯定の説明を先に書く.
- 保証する範囲と保証しない範囲を比べるときは, 表の列にせず,
  保証する範囲を文で書き, 例外は `>` の注意書きにする.

## 作業の記録と本文を分ける

- 本文は, 調査の経緯, 指示の内容, 実施した作業から切り離す.
  該当する語は `指定された`, `今回`, `ユーザー指定`, `作業範囲`, `確認した`, `未実施` である.
- 実施した検証と実施していない検証は, 検証記録のページにまとめる.
- 版の情報は, 冒頭の1行 (`対象: Linux 7.2.8, x86-64`) に限る.

## 書く前と書いた後の手順

1. 書く前に, 読者が抱く疑問を3つ書き出す.
2. 書いた後に, 3つの疑問に本文が答えているか確認する.
3. lint を通した後に, 前提知識のない読者として1節ずつ読む.
   つまずいた語と文を一覧にして直す. lint は表記しか見ないので,
   この読み直しが理解しやすさの最終確認になる.
