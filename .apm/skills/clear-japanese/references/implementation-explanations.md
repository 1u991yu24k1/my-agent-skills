# 実装を読む技術資料の書き方

利用者が呼ぶ API から, 内部の実装までを追う資料に適用する規則である.
カーネルなど, ソースコードを読んで理解する資料が対象になる.
会話や一般文書には適用しない. 検査は `lint_ja.py --profile tech` と `check_diagrams.py` で行う.

## 版と取得元

1. 冒頭の1行に, 対象の版と取得元を書く. 書式は `対象: Linux 7.2.8, x86-64` である.
2. 本文はローカルの絶対パスを含めず, ツリーの場所は frontmatter の `source_tree:` に置く.
3. 草稿の状態は frontmatter の `status: draft` で示す. 本文では, 未ビルドなどの断りを1回にとどめる.
4. 実行結果の扱いは, 検証記録のページに従う.

```yaml
source_version: "linux-7.2.8"
source_tree: /path/to/linux-7.2.8
status: draft
```

## API から実装への導線

1. 内部処理は, 利用者が呼ぶ API からの到達経路で説明する.
2. 経路は, 公開 API, 各段階, 操作対象の構造体の順に示す.
3. 各段階の役割と, 操作する対象を文で書く. 関数名の列挙だけでは説明にならない.
4. 必要に応じて, 停止点と内部状態を読む式を添える. 書き方は観測点の節に従う.
5. 複数のトピックに共通する入口(システムコールの受付など)は, 専用ページにまとめる.
   各ページは, 共通入口へのリンクと, そのトピック固有の処理だけを持つ.

## 経路図の書き方

呼び出しの深さを2文字のインデントで表す. 同じ深さの行は, 呼び出し元へ戻ってから行う次の処理を表す.
右側に `# マーカー パス:行番号` を置く.

| マーカー | 意味 |
|----------|------|
| `def` | 関数の定義位置 |
| `call` | 経路上の呼び出し位置 |
| `gen` | マクロが関数を生成する位置 |

1. 1つの図に定義位置と呼び出し位置が混在してもよい. 区別はマーカーで示し, 但し書きの文は省く.
2. `#` は, その図で最も右まで伸びるコードの末尾から, 1文字空けた列に置く. 全行の `#` を同じ列にそろえる.
3. コメントの前の空白は, 1文字に抑える.
4. 分岐のない経路は, 経路図で書く. mermaid は分岐のある流れに使う.

```text
__x64_sys_write               # gen fs/read_write.c:747
  ksys_write                  # def fs/read_write.c:728
    vfs_write                 # def fs/read_write.c:667
      new_sync_write          # def fs/read_write.c:585
        anon_pipe_write       # def fs/pipe.c:523
          copy_page_from_iter # call fs/pipe.c:617
```

## 出典の書き方

1. 出典は経路図のコメントに一本化する. 図の直後の箇条書きで, 同じ行番号を繰り返す必要はない.
2. 末尾の表には, 図に出ない定義だけを載せる.
3. 行番号は版に固定した値である. 行番号と一緒に, 検索できる語を併記する.

| ソース位置 | 検索語 | 確認する内容 |
|------------|--------|--------------|
| `include/linux/pipe_fs_i.h:26` | `^struct pipe_buffer` | ページを指す配列の要素 |

4. 定義位置, 呼び出し位置, マクロの生成元を区別して書く.

## ソースコードの抜粋

1. 抜粋の前に, 版, `パス:行範囲`, 読む目的を書く.
2. 構造体は, 名前と概要だけで済ませず, 理解に必要な実際の定義を抜粋する.
3. 節の疑問に答える範囲を選ぶ. 関数の全文を転載せず, 答える範囲に絞る.
4. 読むべき点に, 日本語のコメントを付ける. 実コードのコメントは, 日本語で書いてよい.
5. 省略した範囲は, `/* 省略: 縮小時のエラー処理 */` のように内容を書く.
6. 実コードの提示では, 説明用の疑似コードに置き換えた箇所を明記する.
7. 誤解しやすい操作は, 変更する対象と引き継ぐ対象を具体的に書く.
   例: 配列は再確保するが, データページは参照を引き継ぐ.

## 観測点

停止点と式を示すときは, 次の列を持つ表にする.

| 列 | 内容 |
|----|------|
| 停止点 | 関数名, または関数からの復帰直後 |
| ソース位置 | `パス:行番号` |
| 調べる対象 | 引数, フィールドなど |
| 分かること | 見えた値から言えること |

式を並べるコードブロックの前に, 停止する場所と目的を書く.
最適化で値が見えない場合の代替手段は, `>` の注意書きにする.

## 前方参照

1. `後述` は, 1つの節で1回までである.
2. 経路の節が使う構造体は, 初出の文で1文の定義を添える. 詳細の節は, リンクで示す.
3. 定義を先に書けないときは, 参照先の節の見出しを書く. 見出しを書けば `後述` は省ける.

## ハンズオン

1. コード, コンパイルと実行の手順, 期待出力, 結果の読み方の4点を揃える.
2. 解答は, 期待出力の直後に書く.
3. 結果の読み方では, 出力のどの値が, 前の節の図のどの状態に対応するかを書く.
