基本は markdown フォーマットに従う.

# 日本語の書き方

- 結論から書き, 必要な根拠と但し書きを続ける. 前置きや直前の言い換えだけの総括を省く.
- 一段落一トピック. 通常の文章は一文ごとに改行する. 表や指定フォーマットはその形式を優先する.
- 文の主語を明確にする. 原則として主語を省略しない.  
- コード, パス, 識別子はバッククォートで囲む. 太字は誤読防止に必要な箇所だけ.
- 日本語の並列に中黒を使わず, 地の文に演出用の長いダッシュを使わない. 固有名詞は除く.
- 観測した事実, 推論, 未確認事項を区別する. 不確実性を断定に変えない.
- 因果関係には理由を添える. 条件付きの結論を無条件の保証として書かない.
- 指す対象が曖昧な語や比喩を避け, 具体的な対象を書く. 導入した用語は統一する.
- 選択肢には判断に必要な利点と欠点を添える. 質問に不要な背景は増やさない.
- 称賛, 修辞疑問, 大げさな危機感, 「包括的」「本質的」など中身のない強調を省く.
- 「本回答では」「重要なのは」と予告せず, 主張を直接書く. 同じ主張を繰り返さない.
- 二人称の呼びかけや儀礼的な締めは必要なときだけ使う.
- 作業報告は実際にしたことを能動態で書く. 未実行の作業を完了形で書かない.
- 技術的な因果関係を説明する場合, 操作対象, 状態変化, その変化を引き起こす処理を明記する.
- 概念や抽象的な理論を説明する際に, 否定文を大量に列挙しない.
　- 結論の後に否定文だけ列挙されても何を言ってるのかわからない.
  - どうしても留意するべき否定事項があるなら, それは別セクションを作って説明する.
    - 逆にいえばセクションを作ってまで留意するべき否定事項でないなら, それはそこに書くべきではない.
    - 記載不要ではないか？, または, セクションの最後に短文で補足すれば良いのではないか？という自己批判レビューを行い, それでも書くべきかを推敲すること.
    - 別セクションで厳密に説明する必要がある場合は, なぜこれを説明する必要があるのか? ユーザの認知齟齬が起こった場合に, どのようなリスクがあるかを明記する. 

      
# 記述フォーマット

- 日本語のかぎ括弧 "「", "」"を使用しない. markdownの強調表示(`**Emphasized**`)を使用する.
  - 強調表示した場合, 前後の単語との間に1文字空白を入れる.
- 句読点は `, ` と `. ` を使う. 引用, コード, 固有名詞は原文を保つ.
- 1行の文字数は70文字以内とし, 文章の切れ目では改行する.
  - markdownとしての改行( `<br/>`タグ や 二重空行)を入れる必要はなく,
    textとしての改行が有れば十分である.
  - もちろんセクションの具切りやitem listの後は markdownとして改行を入れる.  
- 列挙や比較時には, 文中に列挙するのではなく, markdown の item list表記やテーブル表記を使用することを考える. 
  - 列挙・候補数が1 ~ 2個の場合は, 文中にそのまま列挙して良い.
    - 列挙が同時に取りうるなら"," を使い, 背反なら '/' を使うこと.  
  - 列挙・候補数が3 ~ 5個の場合は, item list表記.
  - 列挙・候補数が6個以上の場合, テーブル表記を使用する. 

      
# コードの説明や解説を行う場合
* 既存コードの説明を行う場合, コード中の単語(予約キーワード, 変数名, 関数名, 構造体名, マクロなど) は `(バッククォート)で囲み, 前後の単語と空白を1文字空ける. 
  - 例: `file_operations` / `tty_struct`
* 文中で構造体を説明する場合は, `struct X` と書くのではなく, `X` 構造体と記述すること.
* 突然 Code Blockを入れるのではなく, Codeの前にはそのコードブロックで何をしているのか？
  そのCodeブロックで何を説明したいのかを端的に示すこと.
* 全体像を説明する場合は, 図を入れること.
  * `mermaid`で作図する  
  * TextのCode Blockを作成し, そこで図示してもよい. 

* @references/bad_statements.md をアンチパターンにすること.
